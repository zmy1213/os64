# 同一镜像的 1 / 2 / 4 核正式测量

测量日期：2026-10-03（Asia/Shanghai；UTC 2026-10-02）。三种配置顺序执行；任一时刻只运行一个基准客体。其他协作代理在采样期间不运行QEMU或构建。宿主其他后台活动没有完全控制，不能声称不存在噪声。

每配置两客体、五场景、每场景31样本，共 **930个正式样本**，另有预热和独立正确性检查。所有样本通过完整结果或逐字节传输校验；465个OS64样本全部物理页回收；所有分块都确认实际在线CPU集合与每核用户执行计数增长。原始data.img未挂载，脚本末尾检查其哈希不变。

主要结论以同镜像宿主等待p50为准：OS64四工作者由一核0.6991秒降到四核0.2741秒，约2.55倍；十二工作者由0.7425降到0.4115秒，约1.80倍。四核十二工作者的Linux约0.2278秒，OS64尚未追平；OS64频繁yield和pipe在四核比双核更慢。实现了实际用户并行，仍需测量并改善多核缩放。

## 实际构建与负载

- OS64：同一个285,776字节内核，`-O2`；用户两边同一编译器、`-Os`、freestanding、明确frame pointer、通用寄存器编译。
- QEMU 10.2.0 / TCG / qemu64 / 128MiB；1、2、4 vCPU分别两客体相同，多核使用`tcg,thread=multi`。
- Linux：官方Alpine客体 `6.18.52-0-virt`；资产、追加initramfs、编译器、QEMU参数和用户ELF摘要完整保存在JSON。
- 四个整数场景都固定总4.8亿次LCG更新；pipe是32MiB、4096B容量与读写块，并逐字节校验，不能把它叫纯copy或一般IPC吞吐。
- ABBA顺序：OS64 16 → Linux 16 → Linux 15 → OS64 15；每分块每场景先预热一次，不计入31。

客体计时从父进程开始创建工作者到等待/回收完成，OS64使用100Hz BSP PIT软件tick，Linux用客体monotonic再换算100Hz。IRQ关闭或等待BKL可延迟OS64软件tick，两个时钟实现不等价；尤其四核客体值比宿主值更短，不能仅靠PIT宣称绝对加速。

宿主等待使用time.monotonic，从逐字发送结束后到再次观察Shell提示符，排除逐字输入，包含剩余计算、串口结果、退出回收、提示符与约10ms轮询；末尾换行后先等约5ms，可能漏掉开始几毫秒。它同样不是纯计算耗时或完整键入到响应的端到端延迟。以下缩放因此明确限定为**本命令协议的宿主等待p50**。

## 同一新镜像自身的缩放

加速比＝本系统一核宿主等待p50 ÷ 同系统多核宿主等待p50。总工作量相同，未拿旧版一核内核当分母。

| os64 | 单工作者 | 0.6966 | 0.6956 | 0.7509 | 1.00× | 0.93× |
| os64 | 四工作者 | 0.6991 | 0.4099 | 0.2741 | 1.71× | 2.55× |
| os64 | 十二工作者 | 0.7425 | 0.4682 | 0.4115 | 1.59× | 1.80× |
| os64 | 四工作者，每65536次yield | 0.8098 | 0.4577 | 0.5081 | 1.77× | 1.59× |
| os64 | 32MiB管道完整校验 | 0.5818 | 0.3193 | 0.4058 | 1.82× | 1.43× |
| linux | 单工作者 | 0.7134 | 0.7312 | 0.7313 | 0.98× | 0.98× |
| linux | 四工作者 | 0.7462 | 0.3993 | 0.2318 | 1.87× | 3.22× |
| linux | 十二工作者 | 0.8416 | 0.4331 | 0.2278 | 1.94× | 3.69× |
| linux | 四工作者，每65536次yield | 1.2002 | 0.5214 | 0.2248 | 2.30× | 5.34× |
| linux | 32MiB管道完整校验 | 0.9404 | 0.5470 | 0.5485 | 1.72× | 1.71× |

OS64四工作者在四核下改善约2.55倍，十二工作者约1.80倍；各核心确实执行用户任务，验证了实际并行。但改善不是线性的，也没有达到这些场景的全面最优。四核十二工作者宿主p50约0.4115秒，Linux约0.2278秒；四核yield约0.5081秒，Linux约0.2248秒。

OS64 yield和pipe四核中位数都比自己的双核差：yield约0.5081对0.4577秒，pipe约0.4058对0.3193秒。当前所有内核服务由大内核锁串行，线程固定核心且不迁移；这些是明确的架构限制。创建/退出、页表、文件描述符、唤醒与时钟处理也在计时区间；本实验不能单独分离每项开销，不能把全部差距未经测量都归因于某一个锁。

单工作者的依赖循环只在一个CPU执行，四核不会拆开这条循环；增加其他核心也增加中断与模拟器调度成本。Linux yield的相对缩放大于4，不表示四核心完成了超出四倍的纯算术；分母的一核调度开销和本次噪声也改变该命令的耗时。

## 长尾、资源与适用范围

所有长样本保留，没有剔除或重采样替换。一核Linux pipe最大宿主等待约10.7364秒，四核OS64四工作者最大约3.7063秒；客体与宿主有相应停顿或范围差。这里只报告观察值，没有定位每次停顿的根因；31样本不足以估计可靠的百分之一尾部，更没有证明调度响应上界或任意负载公平性。

OS64 user_ticks记录Running用户TCB的本地timer计账，包含它执行内核服务的时间；Linux为/proc/stat user+nice jiffies。分块前后都严格增长，验证全部核心承担工作，不能直接把计数相除比较效率。每配置报告列出这些原始前后值。OS64全部155样本/配置页数恢复，只证明这个资源指标；smp_test另外验证堆、绑定、sleep、fault与回收，完整系统回归见[最终验证记录](../validation/README.md)。

这是真x86_64 Linux客体对照，不是macOS宿主充当Linux；但它仍是具体TCG模拟环境。两内核的创建机制、功能集合、编译配置、调度策略和时钟不同；OS64 spawn 与Linux fork+execve均包含在结果内。计时不包括启动。不能将本报告外推为真实硬件、磁盘、网络、一般IPC或整个操作系统速度排名，也不能声称OS64已经最快。

下一步先增加内核锁等待/持有时间和进程创建、ELF装载、切换、唤醒等阶段耗时观测，区分内核成本、固定绑定的负载差异和宿主TCG影响。当前没有这些剖析数据，它们只能是待验证的可能原因，不能断言各自贡献。取得数据后再评估更细的同步、每核队列和迁移；不能通过减少工作量、关闭完整校验或破坏隔离提速。
