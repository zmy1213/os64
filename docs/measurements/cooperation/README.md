# 多核计算与管道协作的功能记录

这是 2026-10-03（Asia/Shanghai）的功能回归记录。它验证多个用户进程在 1、2、4 个 CPU 上计算、传递数据、阻塞和退出时能得到正确结果，也能释放资源。采样时其他代理可能正在运行独立测试，因此这里不是独占宿主的正式性能基准；不能根据 `elapsed_ticks` 计算可靠的加速比。

宿主是 macOS arm64，来宾使用 QEMU 10.2.0、qemu64、128 MiB 内存和 TCG。2/4 CPU 配置启用多线程 TCG。内核按 `-O2`、用户程序按 `-Os` 构建。三个配置使用相同的启动盘和用户 ELF，各自从模板复制一份临时数据盘。

## 每个配置实际做了什么

每个 CPU 配置启动一次来宾，然后顺序执行：

1. 一次 `coop_test 4 2048`：4 个计算子进程，各写入 2048 条记录。
2. 四次 `coop_test 8 128`：每次 8 个计算子进程，各写入 128 条记录，用重复创建、退出和回收检查资源生命周期。
3. 一次完整 `pipe_test`，再执行一次 `badptr`，最后让 Shell 打印存活标记。

计算子进程在每 64 条记录前执行确定的整数运算，并写出完整 64 位结果。父进程用独立的跳跃计算核对结果，逐字节核对载荷，同时检查记录的进程编号、顺序、大小和 CPU 编号。记录交替为 257 B 和 4096 B；父进程每次最多读 777 B，所以不能依赖“一次 read 恰好对应一次 write”。这同时检查了字节流重组和多个写者的小写入原子性。

| 来宾 CPU 数 | 长测次数与规模 | 短测次数与规模 | 合计记录 | 合计数据字节 | `online_mask` / `cpu_mask` / `dispatch_cpu_mask` |
|---|---|---|---:|---:|---|
| 1 | 1 次，4 × 2048 | 4 次，8 × 128 | 12,288 | 26,744,832 | 1 / 1 / 1 |
| 2 | 1 次，4 × 2048 | 4 次，8 × 128 | 12,288 | 26,744,832 | 3 / 3 / 3 |
| 4 | 1 次，4 × 2048 | 4 次，8 × 128 | 12,288 | 26,744,832 | 15 / 15 / 15 |

表中的字节数只统计 `coop_test` 的数据记录，不包含额外的控制消息和 `pipe_test`。每次长测传输 17,829,888 B、8192 条记录；每次短测传输 2,228,736 B、1024 条记录。三种配置合计核对 80,234,496 B、36,864 条记录。

mask 是位集合：CPU0 对应数值 1，CPU1 对应 2，CPU2 对应 4，CPU3 对应 8。`online_mask` 来自内核的在线 CPU 快照；`cpu_mask` 来自计算者实际报告的 CPU；`dispatch_cpu_mask` 来自内核用户调度计数的增量。2 核的 3 和 4 核的 15 说明所有在线 CPU 都实际调度了用户工作。1 核的 1 则说明多个进程在同一核上交替执行。mask 并不测量各核的工作均衡程度，也不证明整个内核并行：管道和其他内核服务仍由大内核锁串行保护。

## 关闭、错误和回收

每次 `coop_test` 另有一个真实阻塞实验：父进程先填满 4096 B 管道，等待内核报告子写者处于 Blocked 状态，然后关闭最后一个读端。五次调用都得到 `blocked_writer_close_epipe_ok`，证明阻塞写者被唤醒并收到 EPIPE，父进程随后完成 wait/reap。

额外的 `pipe_test` 六项均通过：EOF/EPIPE、超过缓冲区的阻塞传输、退出关闭唤醒 EOF、继承描述符共享文件偏移、多写者原子记录和 dup 参数校验。`badptr` 覆盖 IPC、性能快照、UDP（含 syscall40）、SMP 快照41与 sleep 的错误指针及宽度边界；没有出现用户故障或内核崩溃，Shell 能继续执行。

脚本先预热 Shell，再记录基线；每次协作程序返回后都读一次物理页数和内核 heap 活动对象数，最后再检查附加测试后的值。原始串口日志中的七组采样分别是“基线、五次协作之后、附加测试之后”：

| CPU 数 | 每组 `mem_free_pages` | 每组 `heap_active_allocations` | 七组采样是否都相同 |
|---|---:|---:|---|
| 1 | 31,335 | 9 | 是 |
| 2 | 31,332 | 11 | 是 |
| 4 | 31,332 | 15 | 是 |

不同 CPU 配置会保留不同数量的 AP 启动栈和 idle 线程，所以应比较同一配置的前后值。这里没有观察到这些测试遗留物理页或 heap 对象。临时数据盘的前后 SHA256 相同，脚本也检查了原有 `build/agent-cooperation/data.img` 摘要不变。

## 保存的原始证据与构建版本

- `results.json`：脚本原样输出的 15 次协作调用字段，未重算或修改耗时。
- `boot-{1,2,4}cpu.serial.log`：完整原始串口输出，含每次校验、资源采样和存活标记。它保留了终端控制字符。
- `boot-{1,2,4}cpu.qemu.log`：原始 QEMU 错误输出；本轮均为空文件。
- `build-manifest.json`：生成这批所测二进制时保存的构建清单，含源码、启动盘、内核及全部用户 ELF 的 SHA256。
- `SHA256SUMS`：上述归档文件的摘要，可检查复制和后续保存是否改变了原始字节。

本轮所测内核为 **285,328 B**，SHA256 为 `933ce00139ce3b9e012b2f8cc682b8a0086a375d142241f5002855b361810fe4`；所测启动盘摘要为 `d796de7cffd3d78a9cb33998c3c8ab3465a527f6e13a30186b4c3deef374a6f7`。归档时已重新核对实际二进制与清单相符，全部原始输出也与私有测试目录逐字节相同。清单记录 `working_tree_modified=true`，因此仅凭 Git commit 不能重建这个快照。

归档之后集成源码继续修正了 AP 在线总数的发布顺序等细节；更新的默认构建与本轮内核摘要不同。这份记录只证明清单中固定的镜像通过了上述测试，不代替后续最终镜像的完整回归。构建清单保持原样，不用新版本的摘要覆盖旧证据。

285,776 B 的最终集成版本也已完成同规模回归，新记录保存于 [最终功能验证](../validation/README.md)，可按对应清单区分两个版本。

复现当前源码的同类功能回归：

```sh
BUILD_DIR="$PWD/build/coop-repeat" bash scripts/build-stage1-image.sh
BUILD_DIR="$PWD/build/coop-repeat" bash scripts/test-cooperation.sh
```

脚本默认测试 1、2、4 CPU，一次长测加四次短测。新结果会写入这次指定构建目录的 `cooperation-test/`，不会修改本目录已归档的记录。要理解程序和等待协议，可继续读 [IPC 与 Shell 教程](../../IPC_SHELL_TUTORIAL.md)。
