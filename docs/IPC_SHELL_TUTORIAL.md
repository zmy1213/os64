# 从零理解管道、文件描述符和进程协作

本章接在 [从零主教程](BEGINNER_TUTORIAL.md) 后面。先完成启动、`run /bin/echo hello` 和文件保存练习，再来做管道。这里每个命令都在 os64 的 `os64 %` 提示符后输入；不是在 macOS/Linux 宿主终端输入。

目标是弄懂这条命令为什么能工作：

```text
echo one two | cat | wc
```

输出中的 `1 2 8` 分别是换行数、单词数和字节数。`one two` 有七个字节，`echo` 在末尾加一字节换行，总共八个字节。三个程序需要协作，但不需要知道其他程序的名字或内存地址。

## 1. 先理解“输入”和“输出”

把程序想成一个处理字节的工作台：一侧收数据，另一侧交出结果。`cat` 将收到的字节原样交出去，`wc` 统计字节，`echo` 把参数写出去。

通常输入来自键盘，输出去屏幕。重定向可以替换这些连接：

```text
echo redirected text > /ipc.txt
cat < /ipc.txt | wc
echo tail >> /ipc.txt
cat /ipc.txt | wc
```

`>` 创建或清空输出文件，`>>` 在已有内容后追加，`<` 从文件读输入，`|` 将左侧输出接到右侧输入。

最后一个命令应输出 `2 3 21`：第一行 `redirected text`，第二行 `tail`，共三个词、二十一个字节。注意重定向 `>` 会清空旧文件；编辑器的 `save` 使用另一种完整替换接口，并不是调用 `>`。

本系统没有完整 POSIX 终端：单独执行无参数 `run /bin/cat` 会等键盘输入，没有实现 Ctrl-D 终端 EOF。初学练习请给路径、输入重定向或管道。

## 2. 文件描述符不是文件内容

`fd` 是 file descriptor 的缩写，可以译成“文件描述符”。用户程序拿到一个小整数，内核用它查当前进程的表。

| 用户看到的数字 | 默认连接 |
|---|---|
| 0 | 标准输入 stdin，键盘字符流 |
| 1 | 标准输出 stdout，显示到终端 |
| 2 | 标准错误 stderr，也显示到终端 |
| 3～18 | 打开的文件、管道端点或复制出来的连接 |

因此 `read(0, buffer, 512)` 不是“读第零个文件”，而是“沿着当前进程的零号连接取最多五百一十二个字节”。零号连接可以被换成文件或管道，程序不必修改。

零、壹、贰号连接也可以关闭。关闭以后访问会返回错误；内核不能偷偷又接回键盘/屏幕，否则子程序会读错输入或漏掉错误。

源码入口是 [fd.hpp](../kernel/fs/fd.hpp)。为兼容前面教程，普通内部槽仍为 `0..15`，对用户平移成 `3..18`；内部最后三个槽对应公开 `0/1/2`。这是内部布局，不需要应用作者手动换算，`syscall` 层会完成翻译。

## 3. 两层账本：每个进程的标签和共享的打开对象

假设父进程打开文件得到 fd 3，又执行 `dup(3)` 得到 fd 4。两个数字都指向同一份“打开对象”：

```text
父进程 fd 3 ─┐
             ├─ 打开对象：文件、当前 offset、flags、引用数
父进程 fd 4 ─┘
```

`offset` 是“下一次读取从文件第几个字节开始”。沿 fd 3 读四字节后，沿 fd 4 读取会接着往后读，不能又从文件头开始。

`spawn` 创建子进程时复制描述符标签，增加共享对象引用数，不深拷贝文件和 offset：

```text
父 fd 3 ─┐
父 fd 4 ─┼─ 同一个打开对象，references=4
子 fd 3 ─┤
子 fd 4 ─┘
```

关闭一个标签只减一份引用。最后一份引用消失，才释放真正的对象。多个标签里的 offset 必须保持同一份，单纯复制旧 `VfsFile` 结构会让它们各读各的，不能实现这种行为。

目前普通 `spawn` 继承全部连接。Shell 启动管道各段后，会关闭子进程中不需要的 `3+` 连接，只保留已经接好的标准输入输出错误。普通用户程序若自己调用 `spawn`，需要主动关闭继承的多余管道端点。

## 4. pipe 给出一对方向相反的连接

用户库 [os64.hpp](../user/os64.hpp) 提供：

```cpp
int32_t ends[2];
if (pipe(ends) != 0) { /* 创建失败 */ }
// ends[0] 只能读，ends[1] 只能写。
```

管道不是磁盘文件：里面没有路径，不会在重启后存在。它是一块内核内存，装入从写端送来的字节，按同样的顺序从读端取出。这个顺序叫 FIFO，先进去的先出来。

缓冲容量固定为 4096 字节，不会随着程序持续输出而无限占用内存。它用环形队列表示：

- `head` 指向下一个待读字节。
- `count` 表示当前装了多少有效字节。
- 写入位置是 `(head + count) % 4096`。
- 读完一字节，`head` 向前移动，末尾回到零。

`%` 表示取余，例如 `4096 % 4096 = 0`。因此最后一个位置用完以后，可以继续复用开头的位置，不必移动全部已存内容。

一段程序写入三万多字节，另一段程序仍只需要这个四千零九十六字节缓冲；它们轮流写和读。回归程序 [pipe_test.cpp](../user/programs/pipe_test.cpp) 传输 `32768 + 17` 字节，并逐字节检查顺序和内容。

## 5. 阻塞不是忙等

当读端发现管道为空、但还有写端存活，它不能返回 EOF，因为写者可能还没来得及发送。它登记到读等待队列，然后暂时退出 CPU 调度，直到有数据或所有写端关闭。

当写端发现缓冲满了、但还有读端存活，它登记到写等待队列，等待读者腾出空间。

```text
读者：管道为空 → 登记等待 → blocked
写者：写入数据 → 唤醒读者 → 读者变 ready
调度器：选中 ready 的读者 → 从 read 原来的位置继续执行
```

这叫阻塞。它不持续运行 `while (没有数据) {}` 浪费 CPU，其他程序和 Shell 仍能运行。

源码在 [fd.cpp](../kernel/fs/fd.cpp) 的 `pipe_read`、`pipe_write`、`wait_on`、`wake`。底层使用现有调度器的 block/wake 接口，不需要另建一个调度器。

### 为什么登记等待时关中断？

需要防止这种顺序：读者检查为空；写者送来数据但没看到等待者；读者再睡下去。没有下一次写入时，读者可能永远睡着。

在当前单 CPU 实现里，检查、登记、进入阻塞之间暂时关中断；真正换到其他线程之前再开中断。写入和关闭端点会将相应等待者唤醒，恢复后重新检查条件。

这只是本教程单核内核的同步办法。将来支持多核，别的 CPU 仍可同时修改队列，必须增加跨 CPU 的锁；关当前 CPU 中断不能代替它。

## 6. EOF 和 EPIPE 是两件不同的事

| 情况 | read 返回 | write 返回 |
|---|---|---|
| 有数据 | 已读字节数，可以短于请求数量 | — |
| 空，但仍有写端 | 阻塞等待 | — |
| 所有写端关闭且缓冲已耗尽 | 0，表示 EOF | — |
| 有读端且有空间 | — | 写入字节数 |
| 有读端但已满 | — | 阻塞等待 |
| 所有读端关闭 | — | -7，即 `BROKEN_PIPE` |

`read` 返回零是流结束，不能和“现在暂时还没数据”混在一起。读取请求长度为零是另一个特殊情况，也直接返回零。

如果一次大写入已经写了一部分，随后读端消失，返回已写部分的长度；应用需要检查返回值，而不是认为每次 write 都成功写完全部。

### 多个写者的小记录不会被切开

一次 `write` 的长度不超过 4096 字节时，本实现等待足够放下整块数据的空间，然后在一次不可打断的内核临界区复制整块。两个写者的这种小写入不会在记录中间穿插，顺序可能是 A 后 B，也可能是 B 后 A，但不能是半个 A、一个 B、剩下半个 A。

大于 4096 字节的一次写入需要分块、可能等待，允许别的写者在块之间穿插。原子性针对一次 `write`，不是一次高级 `print` 调用或一整行程序输出；拼接多个 `write` 仍可能在调用之间交错。

环形队列读写最多复制两段连续内存：先到缓冲末尾，再从开头继续。这样避免每个字节都算取余，而且一次关中断复制最多 4096 字节。

`pipe_test` 用两个写者各发送六十四条二百五十七字节记录，读者每次仅取一百一十三字节。记录含写者 ID、各自递增序号和可检查的有效载荷；二百五十七不能整除缓冲容量，因此测试会碰到“剩余一点空间但放不下一整条记录”和跨缓冲末尾的情况。逐字节验证可以发现丢失、重复、乱序和记录内部穿插。

Linux 常见的无读端行为还包括 SIGPIPE 信号；本教程目前没有信号系统，只返回 -7。虽然实现了这些小写入约定，仍不能把本章接口等同于完整 POSIX 管道。

## 7. 最容易忘记的步骤：关闭多余端

父进程创建管道后，子进程继承读端和写端。子进程只读，应该关闭自己不需要的写端；父进程只写，应该关闭自己的读端。

```text
父进程：close(读端) → write(写端, 数据) → close(写端)
子进程：close(写端) → 反复 read(读端) → EOF → close(读端)
```

如果子进程留下了写端，它自己就让“写端仍然存在”的条件一直成立。即使父进程已经退出，子进程也可能一直等 EOF。

引用数判断的是所有进程中的全部标签，不是“父进程刚刚 close 了没有”。`dup` 产生的额外标签同样会延长端点生命。

另外，进程退出必须立即释放全部连接，不能等父进程 `waitpid` 才关闭。否则父进程等待管道 EOF、子进程等待父进程回收，可能互相卡住。实现位于 [scheduler.cpp](../kernel/task/scheduler.cpp) 最后一条线程退出的分支。

## 8. dup2 怎么把 stdout 接到管道？

`dup2(old_fd, new_fd)` 将 `new_fd` 接到 `old_fd` 的共享对象。若目标原来有连接，先释放原连接的引用。

```cpp
int saved = dup(1);          // 给原终端输出留一个标签。
int32_t ends[2];
pipe(ends);
dup2(ends[1], 1);            // stdout 现在是管道写端。
// spawn 子进程；它继承这份 stdout。
dup2(saved, 1);              // 父进程恢复终端输出。
close(saved);
```

当 `old_fd == new_fd` 时，合法连接原样保留；不能先关闭再复制，否则源也被关闭了。

`dup(old_fd)` 自动找一个空闲普通槽返回新 fd；没有空槽返回负错误码。不要随意选固定 fd 号备份，因为它可能已经被文件或另一条管道占用。

## 9. Shell 必须先启动所有管段，再等待

对于 `echo one two | cat | wc`，Shell 创建两条管道，启动三个用户进程：

```text
echo stdout → 管道 A → cat stdin
cat stdout  → 管道 B → wc stdin
wc stdout   → 终端
```

必须先启动全部管段，然后关闭父进程持有的多余管道引用，再等待全部子进程结束。不能“启动 echo，等它结束，再启动 cat”：echo 输出多于缓冲容量时会阻塞，而读者还不存在。

同时运行不一定表示多 CPU。当前单 CPU 在多个 ready 进程之间切换，也能让生产者与消费者共同前进。

当前进程表有 16 个槽，线程表有 32 个槽，包含内核 Shell 和 idle 等线程；不是所有槽都能同时分给应用。每个进程公开 fd 范围为 0～18。Shell 一条管道最多四段；超出上限或资源不足要报错并清理已创建连接。

### 当前 Shell 的语法边界

实时 Shell 在固定 `/bin` 路径找用户工具，因此 `echo` 可以省略 `/bin/echo`。裸 `cat`、`echo`、`pwd`、`ls`、`mkdir`、`rm` 在实时环境中运行用户 ELF；启动自测的旧 Shell 仍保留分层观察用的内核版本。`run /bin/echo hello` 保留教程装载诊断。

支持单/双引号与反斜线，以及 `|`、`<`、`>`、`>>`、`2>`、`2>>`、`;`、`&&`、`||`、`&`。`&&` 只在前一条成功时执行后一条，`||` 只在失败时执行。错误状态也适用于旧教程的 `write`、`append`、`touch`、`stat`、`sync`，不能只看输出有没有打印“failed”。

```text
stat /does-not-exist
echo status=$?
```

第二行应输出 `status=1`。`$?` 表示上次状态，零表示成功；错误用法通常为 2，无法找到命令为 127。`$PWD`、`${PWD}` 和 `$PATH` 也可以展开；未知变量变空。展开不会再进行字段拆分或通配符匹配，没有完整环境变量系统。

`sleep 200 &` 在后台启动任务，`jobs` 显示状态并回收完成任务，`wait` 等待全部后台任务。最多记录四个后台作业。没有 `kill`、信号、`fg/bg` 或终端作业控制；后台程序也不要主动抢读键盘输入。

一行最多八个命令，每个命令最多八个参数，每个参数最多六十三字节。解析器缓冲界限为五百一十二字节，但当前终端输入行最多二百五十五字节，所以交互时更早碰到输入界限。管道、重定向和后台执行面向用户 ELF，内核教学诊断命令不能全部当作流处理工具使用。

超过二百五十五字节时，终端继续消费输入直到回车，再显示 `shell: input line too long; entire line discarded`，把状态设为 2。整行被拒绝，前面已经输入的写文件命令也不会执行；剩余字符不会被当成下一行。因为这时已有字符未能放入缓冲，继续退格也不能把这条输入恢复为可执行命令：请回车后重新输入短一点的完整命令。恰好二百五十五字节仍可以执行。

它不是无限制的现代 Shell，也没有完整 Unix 信号、终端作业控制或 POSIX 兼容性。

## 10. 自己运行验证

宿主终端中构建当前镜像并启动：

```sh
make build
make run
```

在 os64 中：

```text
run /bin/pipe_test
```

应依次看到：

```text
pipe_test eof_epipe_ok
pipe_test blocking_32k_ok
pipe_test exit_wakes_eof_ok
pipe_test inherited_offset_ok
pipe_test multiwriter_atomic_ok
pipe_test dup_validation_ok
```

这些检查分别验证：反复释放端点、EOF/无读者错误、超过缓冲的传输、子进程退出唤醒、父子和 dup 共享文件位置、多写者小记录完整性、非法参数拒绝。

自动回归脚本 [test-ipc.py](../scripts/test-ipc.py) 还比较多次运行前后的物理页和内核堆活动分配数，检查真实 Shell 管道和文件重定向、引号/转义、状态与条件、变量、后台任务、错误输出与语法界限。它只使用临时数据盘，原 `build/data.img` 摘要必须保持不变。

测试通过只能说明这些约定已覆盖，不能证明任意应用、所有并发情况或多核环境都正确。下一步可以增加读端中途退出、大写入部分返回、不同优先级写者竞争等实验，并给多核版本设计明确的锁和等待队列规则。
