# 与现代操作系统相比，os64 还缺什么

os64 已经把启动、内存隔离、用户程序、进程协作、文件保存和网络收发接成了可实验的教学系统，并加入最多四 CPU 的基础 SMP：用户程序可以在不同 CPU 上计算，内核共享状态暂由一把大锁保护。继续发展的重点，是验证混合负载的正确性与响应，再逐项扩展并行内核。本章先对照当前源码说明已实现能力，再列出未来阶段；未来验收目标不代表已经完成。

这里以 Linux、BSD 等成熟通用系统的常见能力作参照，具体接口和策略因系统而异。初学者先完成 [主教程](./BEGINNER_TUTORIAL.md)；计算、管道和客体 Linux 对照的实际方法见 [性能教程](./PERFORMANCE_TUTORIAL.md)。

## 1. 先分清程序、进程、线程和 CPU

**程序**是磁盘上的代码，例如 `/bin/bench`。**进程**是它运行时的资源集合：用户地址空间、堆、栈、打开的连接及退出状态。**线程**是调度器安排执行的单位；当前每个用户进程只有一个主线程，内核也有 Shell、idle、网络 worker 等线程。

CPU 执行线程的指令。本章的 CPU 指一个可调度的逻辑执行单元，客体中称为 vCPU；一颗现代多核处理器可以提供多个这样的单元。一个 CPU 同一时刻只执行一个线程；调度器保存 A 的现场、恢复 B 的现场，才能让它们轮流继续。这里的“多个任务都有进展”叫**并发**；两个 CPU 同一时刻执行不同线程，才是**并行**。

当前内核支持最多四个客体 CPU；具体有几个取决于启动配置与发现/启动结果。16 个进程槽和 32 个线程槽表示资源容量，包含内核对象；并不表示 16 或 32 个任务同时执行。每个用户进程只有一条用户线程，首次调度时固定在一颗 CPU 上，暂不迁移。内核 Shell、网络 worker 等内核线程仅在启动 CPU（BSP）上运行。

“发现四 CPU”还不等于“四 CPU 实际执行了用户程序”。syscall 41 的在线 mask、每 CPU 用户调度/运行 tick 和工作程序记录的 CPU 编号用于观察后者；四 CPU 同时计算也不意味着四倍速度。实现及验证入口见 [SMP 教程](./SMP_SCHEDULER_TUTORIAL.md) 和 [进程协作实验](./IPC_SHELL_TUTORIAL.md#12-多核计算和管道一起工作)。

## 2. 已有能力与仍缺的能力

下表的“已有”描述当前实现边界。B 是字节，1KiB 是 1024 字节。相关命令应在更新 `/bin` 后使用；不要为了更新工具清空个人数据盘。

| 线程与同步 | 内核 TCB 与独立栈，通用寄存器及 x87/SSE 现场切换 | 用户线程创建/join、线程局部存储、用户 mutex/条件变量、跨进程共享内存 |

## 3. 优先解决多进程计算与调度

### 3.1 进程多了，为什么不一定更快

把一亿两千万次计算分别分给 1、4、12 个进程，总计算量仍是一亿两千万次。单 CPU 必须逐个执行这些指令，还要创建进程、切换现场和回收资源。因此工作者数量增加，耗时可能变长。下面是 **os64 中**的等总量实验；先记清当前以几个 CPU 启动：

```text
run /bin/bench 1 120000000 0
run /bin/bench 4 30000000 0
run /bin/bench 12 10000000 0
```

多进程在单 CPU 上仍有价值：一个任务等待管道、磁盘或网络时，另一个可以计算；交互任务也不必等长计算结束。纯计算、等待 I/O、任务创建是不同工作负载，不能拿一个实验回答所有问题。

用多个 CPU 时，不同用户进程可以同时计算。但所有 syscall、共享管道操作、文件事务与内核分配仍由 BKL 串行执行；通信越频繁，等待锁和唤醒的成本越明显。固定归属还意味着一个 CPU 上的进程退出后，其他 CPU 的工作不会自动迁来填空。新多核基准必须同时报告 CPU 配置、实际调度分布和完整结果。

还有算法限制：如果后一步必须等待前一步，即使增加 CPU，也不能同时执行这一段。将工作分块、汇总结果、共享锁和等待会形成额外成本；四个 CPU 不自动等于四倍速度。第一目标始终是每块计算恰好执行一次且结果正确。

### 3.2 能轮流前进，还不等于公平或响应及时

当前同优先级轮转方便理解，但高优先级持续就绪时，低优先级可能长期排不到。内核操作仍依靠明确的调度点；长时间文件事务或临界区可能延迟唤醒者。固定 10ms 左右的 PIT 节拍也限制了观测精度，不能把“一个 tick”直接当作精确的 10.000ms 实测。

公平性问的是：“同样需要 CPU 的任务，长期得到的时间份额是否符合约定？”响应性问的是：“任务已经可以运行后，等多久才真正获得 CPU？”吞吐量问的是：“每秒完成多少总工作？”一个策略可能提高吞吐却拖慢短任务，因此需要同时看这些指标。

Linux 的 EEVDF 通过虚拟运行时间跟踪任务得到的 CPU 份额，再结合虚拟截止时间选择可运行任务，兼顾公平与响应。它是研究调度策略的参照；os64 当前没有实现 EEVDF，也没有实时截止时间保证。[Linux EEVDF 官方说明](https://docs.kernel.org/scheduler/sched-eevdf.html)

现有 `sched_test` 检查八个工作者在首个完成之前都报告进度。这能发现明显的串行跑完再轮到下一个等问题；管道记录本身也可能使工作者阻塞，因此不能据此证明精确 CPU 份额或任意负载的公平性。需要补充每任务运行时间、就绪等待时间和唤醒至运行的延迟统计。

### 3.3 测量结果必须带条件

仓库已有的 31 样本基准对照同一 QEMU TCG、1 vCPU、128MiB 的 os64 与真实 Linux 客体，使用相同计算源码并核对计算机器码。这是有效的**单核历史证据**，不是新版四 CPU 的测量结果。新增 SMP 不会改变旧报告的 CPU 配置，也不能把旧样本乘以四或改标题来充当新数据。

多核对照需要双方用相同 CPU 数与 TCG 模式重新运行，保持总工作量，检查计算正确性、实际 CPU 执行分布和资源回收。无论哪份报告，它比较的都是这些客体、这些程序和这些参数；双方内核配置、创建进程的方法与时钟实现仍有差别。不能据此声称 os64 的整个系统比 Linux 快，或已经具有现代系统的功能。

每次结果需要保留构建/资产哈希、工作量、正确性、重复样本、资源回收及日志。31 次样本取最近秩 p99 时实际上取到最大值；它能暴露偶发停顿，但不能可靠估计长期运行的百分之一尾部。100Hz tick 和未经校准的虚拟 TSC 也不能给出可信的亚毫秒或跨 CPU 纳秒结论。

下一份实验应加入“多个持续计算任务 + 一个周期短任务 + 网络或管道”：既记录总吞吐，也记录短任务延迟的 p50/p99/最大值，以及任务是否失去进展。测试目标和失败阈值要在运行前确定，并报告实际条件。完整计量步骤见 [性能教程](./PERFORMANCE_TUTORIAL.md)。

## 4. 用户线程、共享内存和同步为什么要一起设计

不同进程目前有独立用户页。同一个虚拟地址可以指向不同物理页；继承 fd 只共享文件或管道对象，不会让父子自动共享普通变量。

用户线程则通常共享同一进程的地址空间，同时拥有各自的寄存器和栈。A 线程释放的内存若 B 还在读取，就会出现错误；用户分配器当前的单线程链表也不能直接被两个线程同时修改。

共享计数器 `counter += 1` 可以分成读旧值、加一、写回。两个执行者都读到 7，最后都写 8，就丢了一次更新。**mutex（互斥锁）**让同一时刻只有一个执行者操作这份状态；**条件变量**让不满足条件的执行者睡眠，满足后再唤醒。单核抢占同样可能出现这种交错，不必等到多核才测试同步。

“先检查为空、随后才登记睡眠”还有漏掉唤醒的风险。因此对象状态、等待登记、解锁与阻塞必须遵守统一协议。现有 pipe 的等待队列是可追踪的小例子，未来线程、共享内存和 socket 等待可以复用其思路，但需要重新审查对象寿命和锁规则。

MIT 的 xv6 教材将 locking、scheduling、sleep/wakeup 与文件系统放在一个小内核中讲解，适合先读“状态由谁保护、锁何时释放”，再读成熟系统的大量策略。当前 xv6 教材基于多核 RISC-V；学习其协议后，仍要实现 os64 的 x86_64 启动、中断和页表细节。[MIT xv6 教材](https://mit-pdos.github.io/xv6-riscv-book/)、[MIT 官方 xv6 入口与源码](https://pdos.csail.mit.edu/6.1810/2025/xv6.html)

## 5. 已完成的 SMP 基础与下一层工作

SMP 表示多个 CPU 共同运行一个内核。`cli` 只关闭本 CPU 中断，第二颗 CPU 不会因此停止。本版新增 BKL，使不同 CPU 依次进入共享内核路径；每 CPU 独立保存当前线程、栈和切换状态。BKL 不覆盖用户计算，所以一颗 CPU 正在用户态计算时，另一颗仍可运行自己的用户进程。

阻塞时先在锁内登记等待、标记 blocked，并保持锁到旧栈保存和切换完成；目标上下文回用户态或 idle 等待时才释放。恢复阻塞调用前重新持锁。它不是拿着锁原地睡眠，也不能在旧 RSP 仍未保存时先放锁；后一种做法可能让旧线程被另一 CPU 提前唤醒，导致同一线程在两 CPU 上运行。

| 基础 | 零基础理解 | 当前实现及下一步 |
| --- | --- | --- |
| 发现和启动 CPU | 知道还有谁，并让它从入口开始运行 | 已有 ACPI MADT/MP 拓扑与最多四 CPU 的 AP 启动；无 CPU 热插拔和 x2APIC |
| 每 CPU 状态 | 每个执行者有自己的工作台 | 已有独立栈、TSS、当前线程、idle、本地调度状态；FPU/CR3 随线程保存恢复 |
| 跨 CPU 同步 | 两颗 CPU 不同时改坏一本账 | BKL 保护共享状态；下一步才是独立对象锁、取得顺序和锁竞争观测 |
| 跨 CPU 通知 | 唤醒另一个 CPU，或要求它处理变化 | 已有 IPI/远端唤醒；各 CPU 选择符合固定归属的线程 |
| 页表缓存同步 | 旧地址已经撤销，别人也必须知道 | 目前用户地址空间只在固定 CPU 执行；未实现 TLB shootdown，不能直接开放跨 CPU 共享地址空间/迁移 |
| 调度与迁移 | 空闲者接工作，忙者交出一部分 | 首次调度选较轻 CPU 后固定；仍缺动态迁移、工作窃取和完整负载均衡 |

锁还要有取得顺序。将来拆分 BKL 时，不能拿着对象自旋锁去做会睡眠的操作，否则别人可能永远等不到释放；必须设计锁释放、等待登记和对象引用的完整协议。当前 BKL 的切换交接规则是一项专门设计，不能直接套用到每个对象自旋锁。Linux 区分睡眠锁、CPU 本地保护和自旋锁，并规定嵌套规则；应学习这些约束后再拆锁。[Linux 锁类型与规则](https://docs.kernel.org/locking/locktypes.html)

网络也要随 SMP 重新设计。Linux 的 RSS/RPS/XPS 等机制让收发处理分布到 CPU 或网卡队列；当前 os64 的单队列设备、worker 与全局协议状态没有这样的扩展能力。多队列会改变锁竞争、缓存位置与中断分配，需要计算负载和网络负载一起测量。[Linux 网络扩展官方说明](https://docs.kernel.org/networking/scaling.html)

## 6. 建议的五个后续阶段

以下全部是**未来工作**。每阶段可以拆成多个小实现；先写可观察的验收程序，再增加接口。新阶段必须保留现有计算结果、页/堆回收、用户故障隔离和个人数据盘保护测试。

### 阶段一：补齐每 CPU 调度证据与策略

增加每任务 CPU 时间、就绪等待、唤醒延迟统计；制定同优先级份额与低优先级进展规则，再考虑老化或权重策略。先控制内核长操作的预算，不急着复制完整 Linux 调度器。

验收：8 个持续计算者加一个周期短任务；核对完整结果和所有任务进展，连续收集至少 1000 次唤醒样本，报告 p50/p99/最大等待。另做高/低优先级竞争，要求约定观察窗口内低优先级仍有进展。实验前设定延迟和份额允许偏差；这些是新的测试目标，不是已有保证。

### 阶段二：固定 CPU 的用户线程与可验证同步

明确 create/join、线程栈、退出/故障如何影响进程、共享 fd 和堆的规则；先让同一地址空间的用户线程留在同一 CPU，添加 mutex/条件等待，再决定共享内存接口。使用户分配器符合多线程规则，不能只增加一个 thread syscall 就宣布完成。让同一地址空间跨 CPU 执行或远端修改映射，必须等下一阶段补齐缓存失效协议。不同进程也可分别映射同一物理页，但这仍需要授权、每个映射的寿命与同步规则；本版尚未提供这种接口。

验收：8 个线程分别在锁内增加计数器 100 万次，最后必须为 800 万；生产者/消费者在不同唤醒顺序下保持每条记录恰好一次。反复创建/join 1000 轮后页、栈和对象回收；新线程寄存器初始状态正确。跨进程共享页要另测关闭/退出后最后一个引用才回收，以及无权进程不能取得映射。

### 阶段三：扩展并行内核、迁移与共享页

在现有四 CPU、固定归属、BKL 基础上，先加入锁持有/等待时间观测、TLB shootdown 和线程迁移安全协议，再逐项拆出独立对象锁与动态负载均衡。普通 pipe 操作当前正确地串行进入内核；拆锁后仍要保留 EOF、EPIPE、小写入原子性和关闭唤醒，不能只看吞吐增加。

验收：在 2/4 vCPU 客体中确认所有 CPU 实际执行任务；固定总工作量分块，每块恰好完成一次、结果完整，记录多轮并行吞吐而非只看启动打印。迁移、同时分配/释放、pipe 和故障退出重复至少 1000 轮；远端撤销映射后不能继续使用旧 TLB 指向已回收页。任何加速都必须同时通过隔离与回收检查，不要求未经测量的“核心数倍加速”。

### 阶段四：统一 I/O 等待与网络协作

在已有 UDP 阻塞接收/超时基础上，把 socket 纳入 FD 和统一多连接等待对象，明确 close/退出怎样唤醒等待者。保留有界队列、背压和丢包计数；TCP 的连接、重传、流量控制作为独立后续子阶段。

验收：一边持续计算，一边等待多个 pipe/socket；检查数据内容、超时、关闭后唤醒及进程归属。受控 UDP 丢包应有统计且无内存泄漏；实现 TCP 后，注入丢包/重复/乱序，接收字节流必须完整有序，连接失败后能释放全部资源。吞吐提升同时报告计算任务与网络尾延迟。

### 阶段五：应用接口与持久化可靠性

按明确接口增加 exec/环境变量、信号与进程组/TTY，再逐项补静态用户运行库，尝试移植一个小命令行应用。存储侧单独设计 journal（事务日志）与恢复规则；图形桌面、新硬件驱动和动态链接仍是更远的工程目标。

验收：程序替换后继承/关闭连接符合规定；前台中断、后台等待和终端归属可观察，移植应用无需改内核即可运行其约定功能。文件更新期间在多个写入点强制终止虚拟机，重启验证文件处于规定的旧/新状态、空间账本一致；新增权限后另测未经授权的访问。程序能运行和断电恢复要分别验收。

## 7. 怎样使用开源资料继续学习

| 资料 | 建议先看什么 | 与 os64 对照时的边界 |
| --- | --- | --- |
| [MIT xv6 教材](https://mit-pdos.github.io/xv6-riscv-book/)、[源码](https://github.com/mit-pdos/xv6-riscv) | locks、sleep/wakeup、scheduling、文件系统日志 | 小型教学系统适合追完整协议；RISC-V 硬件代码不能直接用于 x86_64 |
| [Linux EEVDF](https://docs.kernel.org/scheduler/sched-eevdf.html)、[锁规则](https://docs.kernel.org/locking/locktypes.html) | 份额/延迟为什么要分开，持锁路径允许做什么 | 先建立本项目可测目标，再研究策略；不声称现有轮转等同 Linux |
| [Linux 网络文档](https://docs.kernel.org/networking/index.html)、[多 CPU 网络扩展](https://docs.kernel.org/networking/scaling.html) | 队列、收发预算、中断分布与竞争 | 当前单队列 UDP 的成功测试不足以证明多核高速网络 |
| [OpenBSD ksh 手册](https://man.openbsd.org/ksh)、[源码入口说明](https://raw.githubusercontent.com/openbsd/src/master/bin/ksh/README) | 引号、展开、条件执行与 job control 的公开语义，再追执行路径 | 完整 shell 依赖环境、信号、进程组和 tty 等接口；当前 jobs/wait 只是有限跟踪 |

OpenBSD ksh 的手册明确描述了脚本结构、展开和终端作业控制。可以用它逐条制定未来兼容测试，但本项目仅实现了自己的有限语法，不能因几个命令形式相同就称为 POSIX shell。[OpenBSD ksh 官方手册](https://man.openbsd.org/ksh)

每实现一项，更新“已有能力”、对应教程和可运行验收。读者应能从命令、结果、源码与测试判断它何时完成，而不是靠功能名称判断。
